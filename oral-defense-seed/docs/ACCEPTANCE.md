# 受け入れ条件

2026-09-15。[ADR](adr/0001-coach-led-shadowing.md)と[設計](DESIGN.md)に対する目標。標準ループの状態制御を自動試験済み。実provider品質・録音を含む全条件の合格は未達（[検証記録](VALIDATION.md#2026-09-15-coach主導の標準ループ)参照）。VALIDATION.mdのAC番号は既存実装の試験識別子で、以下の合格証拠ではない。

|---|---|---|---|

## 計画レビューによる補足（2026-09-22）

今回のMVPはSH条件と以下のRV条件で判定する。FS01〜FS04はMVP後の #8、実音響評価器の精度・校正は別のP0で扱う。
RV条件は既存SH条件を具体化するもので、所見への対応時期は[IMPLEMENTATION.md](IMPLEMENTATION.md)、根拠は[REVIEW.md](REVIEW.md)を参照する。

| ID | 対応する既存条件 | 追加する合格条件・証拠 |
|---|---|---|
| RV01 | SH05/SH07/SH12/SH15 | #9-AでDB契約ごとの実装・試験・不足を記録。共有exportの私的情報除外をsentinelで確認。#9-Bで旧DB移行、削除回復、別data dirへのbackup/restore後のアプリ読取と音声/資料整合性を確認 |
| RV02 | SH10 | 既知の4質問と出典/本人情報の取り違えケースについて判定基準を変更前に固定し、実モデル出力・設定を保存。未提示の成果・数値・計画・実施状況の断定を認めず、既知の失敗を再発させない。一般的な無誤謬性は主張しない |
| RV03 | SH11 | 資料準備から開始までの手順が明示され、生成失敗・二重開始・reloadでもPack/manifest/採用segmentが一致。provider入力とexportが同じ固定版を使い、開始後の資料変更で背景が変わらない |
| RV04 | SH03/SH05/SH07/SH09/SH13/SH14 | 操作表にstage・対象版・pause・遅延結果の扱いがある。支援生成中のターン進行、再生完了と案採用の競合、単独復唱中の音声制御をAPI/E2Eで確認。閲覧だけで返答を確定しない |
| RV05 | SH06/SH09/SH15 | 保持保証・容量・期限・破棄の契約があり、upload失敗後のターン/セッション切替、reload/終了の各ケースが宣言した保証と一致。同じ録音の再送は同じキー・所属で保存され、削除後に復活しない |
| RV06 | SH14/SH16 | 13往復以上で継続とprovider入力予算を確認。51ターン以上のブラウザfixtureで全履歴へ重複/欠落なく到達し、新ターン追加・reload後も過去録音/評価を参照可能。総数と取得済み件数を区別 |
| RV07 | SH01〜SH16の完成判定 | 条件→担当Issue→検証結果→未達の対応を確認し、IMPLEMENTATION/Issue/README/VALIDATIONの範囲と状態が一致。FS/P0未達を会話MVPの合否に混同しない |

各条件の証拠には対象commit、環境/provider、試験ケース、結果、制限を記載する。
人間の実利用は #7-A の短い途中確認と #7-B の最終6往復を分けて記録する。同じ有効な結果を複数条件で参照してよい。

2026-09-22のRV01/SH12の共有範囲、DB復元fixtureと関連回帰は[VALIDATION](VALIDATION.md#2026-09-22-rv01共有exportとbackuprestore)、DB子Issue条件ごとの証拠・不足は[DB_AUDIT](DB_AUDIT.md)を参照。共有export修正と復元fixtureの成功は、RV01全体や #9-B/MVPの合格を意味しない。
